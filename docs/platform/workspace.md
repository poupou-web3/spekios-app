# Customer workspace and operator back office

The customer workspace runs at **http://127.0.0.1:18080**, embedded in the Rust API. The operator back office is a separate deployment, its own nginx container at **http://127.0.0.1:18083**, which proxies `/v1` to the same API; it is never shipped with the workspace and the workspace has no links to it. Both use the existing PostgreSQL records, private evidence bucket and ClickHouse export. The frontends are native ES modules without a build step: see [apps/web](../../apps/web/README.md), [apps/backoffice](../../apps/backoffice/README.md) and the shared [packages/web-ui](../../packages/web-ui/README.md). Browser automation stays in the separate TypeScript/Playwright worker.

## Open the app

```sh
.tools/bin/just dev
```

Open the URL above. This machine enables `SCOUT_DEV_AUTH_BYPASS=true` in the private `.env`, so the workspace and back office open directly during development. The browser discovers this mode through `/v1/auth-mode` and sends no bearer token. Compose still publishes the API only on loopback; development access requires a literal localhost host and same-origin browser requests. The interface labels this mode **Local development · sign-in disabled**.

Set `SCOUT_DEV_AUTH_BYPASS=false` and run `just dev` to restore the token screen. The default is false in source/example configuration, and the provider-fixture overlay explicitly disables bypass for authentication tests. In normal mode, enter a workspace access token in the workspace, or `SCOUT_API_TOKEN` from the private `.env` for local development; the back office accepts only the operator token. Each app keeps its token in the current tab's session storage under its own key and sends it as a Bearer header. Neither mode embeds tokens in static assets or URLs, and provider/storage keys stay on the server.

Existing runs can be reviewed immediately. Live exploration requires a provider key in `.env` and a matching model selection; see [model gateway](./model-gateway.md). Workspace **Settings** has one page per section (`#/settings/models`, `exploration`, `limits`, `data`, `appearance`): nonsecret model and execution preferences, provider availability, app memory, saved app sessions and the appearance choice. One draft spans the sections and a save bar lists the sections with unsaved changes. Credentials, allowed origins, worker heartbeat and other server policy are read-only in the back office. Change credentials or origins in `.env` and apply them with `just dev`. A configured key is not proof of a successful live provider request, and saving defaults makes no model call or connection test. No provider account is connected automatically. ChatGPT/Claude subscription authentication is still pending. [Private app login](../exploration/private-login.md) is available from the queued worker, with optional encrypted session reuse; Google/external identity-provider handoff remains pending.

## Appearance

Every page offers a **Match system / Light / Dark** control in its header, and the workspace repeats it under **Settings → Appearance**. Match system is the default and follows the operating system. A light or dark choice is stored in this browser (`localStorage` key `scout.theme`) and applied before first paint by `/assets/ui/theme-init.js`, so pages do not flash. Colors are defined once in `packages/web-ui/src/styles/tokens.css` with `light-dark()`; the brand is cobalt, and green stays reserved for passing checks.

## User workspace

- Submit only an application URL from the **Paste a URL.** landing (or **New test** in the sidebar). A bare host such as `app.example.com/login` is sent as `https://…` (`localhost`, loopback addresses, `host.docker.internal` and dot-less names with a port such as `larchwood:8084` as `http://…`); malformed input is explained under the field instead of being submitted. For a `localhost` address, the line under the field explains that the test browser runs in Docker and suggests the matching `host.docker.internal` address. A status line under the field shows whether the model, gateway and browser worker are ready. Screen size, sign-in and automatic rechecks sit behind the options summary below it. An empty workspace shows a three-step explanation instead of the runs table. Saved provider, model and action-limit settings are applied at admission. Public https sites are accepted; private, HTTP and internal addresses still have to be listed in `SCOUT_ALLOWED_ORIGINS`. The optional viewport picker selects desktop, tablet or mobile; the saved default applies otherwise. A setup checklist explains the gateway, model connection and worker requirements.
- Launches remain in the workspace, display the queued job, and automatically open its run when the worker assigns one. Explicit navigation cancels that automatic follow behavior. A job that finishes or fails before creating a run remains visible with its terminal state and any recorded error.
- Search the latest 50 runs by application, run or model; filter execution/review status and live versus fixture data. Test fixtures are labeled **TEST DATA**. Pending and confirmed finding counts come from server-derived summaries for original explorer runs within those latest 50 records; replay runs do not create duplicate finding counts. Active-run and screenshot totals have their separate workspace-wide scope labeled on the cards.
- Review every action's frozen expectation and observed outcome, before/after PNGs, exact difference mask and unique evidence IDs. Fill/select/check/uncheck actions have explicit timeline labels; Inspect action shows their exact parameters. **Compare** shows Before and After together on desktop and stacked on mobile, each with its own capture ID, copy control and full-resolution viewer. Screenshots are displayed independently; the UI does not claim automatic alignment or treat a difference as a defect. Capturing/pending-upload states remain distinct from permanent evidence gaps, and recorded IDs remain visible. Individual Before, After, Difference mask and settling-frame views remain available.
- Open screenshots, masks and settling frames in the evidence drawer to inspect their actual native pixels with scrolling, or switch to fitting the panel. The original PNG is unchanged. **Previous / Next** follows the visible action list or active Findings filter, displays its position and disables the list boundaries. Moving between actions keeps Compare selected; a previously selected settling frame is cleared.
- Inspect ranked next actions, score components expressed through selection reasons, discovery paths and the first-parent tree in the Flow tab. The graph retains recorded transitions, return paths, visited controls and blocked/unvisited controls. Scores are labeled as uncalibrated rather than measured probabilities.
- Start one fresh-browser reproduction for an eligible suspected issue; open the resulting run and compare separate evidence. Reproduced candidates still require review before confirmation.
- Optionally enable **Automatically recheck suspected bugs** beside the URL launch. It is off by default and keeps an explicit per-tab choice through refresh and URL changes. The help explains the additional usage bounds before launch: two cases and twelve replay actions in total by default, with every prerequisite action counted. The original source run shows an **Automatic checks** panel with reservation reasons, child runs, outcomes and source-action links. An automatic replay shows its parent lineage. Pending or queued automatic work suppresses duplicate manual replay controls.
- Use **Export report** to download readable Markdown, an evidence ZIP or the existing full run JSON. Opening the drawer pins the loaded snapshot; an active run is labeled partial. The ZIP carries verified selected-run PNGs, JSON artifacts and a SHA-256 manifest, with missing or invalid evidence listed as gaps. Related replay evidence stays in its own run. Standalone Markdown has no image links; ZIP Markdown uses fixed relative paths to included images. Export makes no model call and does not approve data for training. See [portable reports](../runtime/reports.md).

The run summary separates execution state, application context and action budget. Its meter reports allowed browser actions used; it is not a percentage of tested application coverage. Actions, Findings and Flow tabs support keyboard selection. Automatic refresh preserves active text entry, selection and IME composition, open evidence/access disclosures, and relevant timeline/table/drawer scroll positions. Refresh timestamps identify the loaded snapshot; failed refreshes retain the last available data with an error notice.

The export drawer reports verification progress and supports cancellation. Closing it, navigating away or disconnecting stops an unfinished download without changing the browser run. ZIP bounds are 256 evidence entries, 8 MiB per file, 64 MiB per archive and two minutes; document-size and aggregate checks can also stop an oversized export. Inspect `manifest.json` for gaps even when the ZIP downloaded successfully. Provider payloads and saved private sign-in sessions are not added. Raw JSON retains the existing authenticated report projection, including recorded application data, so review it before sharing. Downloads stay local; they are not persisted as new bucket objects or database export records.

For the bundled controlled app, run `just fixture` and submit `http://exploration-fixture:8082/branches`. The browser runs inside Compose, so the host preview `http://127.0.0.1:18082` is not its target address. Other apps need a reachable container address and an exact origin in `SCOUT_ALLOWED_ORIGINS`. This is still the bounded explorer described in [URL exploration](../exploration/overview.md). Native text entry, dropdowns, checkbox/radio changes and scrolling are described in [browser interactions](../exploration/interactions.md). `just explore-matrix URL` runs all three responsive viewport profiles at once, one browser slot each; each appears as a separate run in the GUI. See [the planner guide](../exploration/planner.md) for ranking, return routing and replanning limits.

## Operator back office

Open **http://127.0.0.1:18083** (`just backoffice`). It is the service provider's console, built from `apps/backoffice` and the shared kit and served by its own container (`infra/backoffice`). Publish it only on a private network or VPN. Sign in with `SCOUT_API_TOKEN`, or open it directly with local development access. Views are addressable as `#/overview`, `#/jobs`, `#/models/<run>`, `#/events/<run>` and `#/connections`. Runs are inspected inside the back office; it does not link into the customer workspace.

The overview separates worker availability, model-gateway readiness, evidence delivery and event delivery, with attention signals that link to the relevant view. It shows run counts, worker heartbeats, pending screenshot/artifact/model payload uploads, and runtime/model events awaiting ClickHouse delivery. Readiness describes the local dispatcher and configured connections. PostgreSQL supplies durable upload/export counters; these snapshots do not directly probe bucket, provider or ClickHouse health. A previous export acknowledgement is not a current service-health test.

Browser jobs expose search, execution-status and live/simulated-mode filters across the latest 50 returned jobs, with worker assignment, launch/duration details, errors, cancellation and result links. Automatic reproduction jobs are labeled and link to their parent exploration when it is in the recent queue view; otherwise the lineage drawer preserves the parent job ID.

Select a run to inspect model requests with provider, state, purpose and search filters. Model activity separates stable logical request IDs from actual provider attempts; recorded attempts and their nullable usage come from the run report, rather than being inferred from request state. The drawer exposes frozen input, response text, attempt details, stored payload keys and event history. Event search applies to the selected run's ordered execution events. These filters do not change whole-run usage totals.

The usage overview follows the gateway's current live or simulated mode; per-run usage stays attached to that run. Each reproduction has its own usage totals. Missing usage/cost remains **Unknown**; incomplete sums display **≥** to identify a known subtotal. Connections shows read-only provider credentials status, scope, server policy and browser workers. Exploration defaults and saved app sessions are customer data and live in workspace Settings.

The API does not yet distinguish these deployments by permission: a workspace manager token can still call `/v1/operations` and read its own model requests, as the agent-identity contract tests expect. Restricting those endpoints to the operator principal is a separate API change.

## Save exploration defaults

Open **Settings** in the workspace. Supported fields are:

| Preference | Accepted values |
| --- | --- |
| Your models (**Models**) | Up to 30 models to choose from, each a provider, a model ID, an optional name of up to 60 characters and optional input and output prices in USD per million tokens (0–10,000; empty keeps the known price) used for cost estimates. A provider can have several models, such as two Meta AI models; each provider and model ID is listed once. The models in use stay listed. Jobs do not freeze the list |
| Exploration model (**Models**) | A model from the list: OpenRouter, OpenAI, Anthropic or Meta AI, with an ID of up to 200 characters using letters, numbers, `/ : . _ -`; surrounding spaces are trimmed |
| Navigation model (**Models**) | Optional cheaper model from the list for opening pages, following links and scrolling; otherwise the exploration model does everything |
| Limits | Optional maximum actions (1–10,000), minutes (1–10,080), reported tokens and reported cost; empty means no limit. Stop after 50 consecutive actions with nothing new, unless turned off |
| Limit overrides | Different limits for a project, a model or a model within a project; the most specific matching override wins |
| Default viewport | Desktop, tablet or mobile |
| Restrict OpenRouter to free model IDs | Requires `openrouter/free` or a model ending in `:free`; direct-provider calls, including Meta AI, use their own API billing |
| Automatic checks by default | Optional boolean; each URL launch can explicitly override it |
| Maximum automatic cases | Integer from 1 to 3 |
| Total additional replay actions | Integer from 1 to 100 across complete selected paths |
| Remember explored pages and controls across runs | Boolean, on by default; agents and API clients can override it per exploration with `app_memory` |

**Save defaults** creates an append-only PostgreSQL revision and applies it to future browser-job admissions without restarting services. Queued and running jobs retain their original settings, as do exact retries of an already admitted job UUID. Existing per-launch viewport and automatic-check choices continue to override defaults. Saved preferences survive service restarts. Environment values provide the initial defaults; after a saved revision exists, its editable fields take precedence. Credentials, origins, execution mode and network policy continue to come from the operator configuration. Direct recorder CLI exploration continues to use its environment configuration.

**Settings → Memory & sessions** lists what earlier runs remembered for each app, screen size and sign-in state (pages, tried and untried controls, runs, last update) from `GET /v1/app-memory`. **Forget** calls `POST /v1/app-memory/{scope_id}/forget` and deletes only that derived memory; recorded runs and evidence stay. A scope used by a running test cannot be forgotten until it finishes. The run heading shows whether earlier runs guided it, and the Flow tab labels a reopened remembered page as **Reopening a page from earlier runs**. See [memory across runs](../exploration/planner.md#memory-across-runs).

Dirty drafts survive polling. Inputs are disabled during a save, duplicate clicks make one request, and an ambiguous response offers **Retry save** with the same request UUID and values. A concurrent revision preserves the draft and requires an explicit choice to discard it or keep the edits on the latest revision. An idempotent receipt may describe an older saved revision; the UI reads the latest state after acknowledgement and prevents older polling results from rolling it back. Saved defaults and current revision are available through authenticated `GET /v1/exploration-settings`; updates use `POST` on that same endpoint. See [the API contract](../../apps/api/README.md#exploration-settings).

## Queue and recovery

`browser_jobs` stores an immutable request, settings snapshot and execution mode. A UUID makes admission idempotent, including retrying an uncertain browser response. The worker claims queued jobs from every workspace member, up to `SCOUT_BROWSER_SLOTS` running jobs (1–8). Each running job holds a Postgres advisory lock on its own connection; when that connection drops, another pass can recover the job. Heartbeats update every five seconds and become unavailable after twenty seconds without an update.

Queued jobs survive restarts. If the worker dies during a run, recovery preserves existing evidence and does not repeat a dispatched action. An exploration with actions still in its budget is queued again as a new run, at most three times, and plans from the pages the interrupted runs already recorded. Reproductions, fix checks, cancellations and explorations that have used the continuation limit or the action budget stay interrupted. The worker exports recovery events to ClickHouse before becoming idle, even when no next job is queued. Live and simulated jobs run only when the gateway is in the matching mode. Private sign-in is still one login at a time. Kubernetes manifests remain future work.

Automatic scheduling applies only to completed original explorations launched through the queue. Reservations survive restarts and remain within the source launch's frozen limits. Temporary provider, storage or queue failures leave checks deferred; invalid paths, missing saved sessions, scope changes or completed reviews can skip them. A cancelled or interrupted check is never automatically retried. The original immutable evidence manifest remains unchanged; the current API report overlays later task decisions, child jobs, reproduction outcomes and cancellation state. See [automatic reproduction](../exploration/automatic-reproduction.md).

Screenshot and artifact endpoints look up the UUID within the authenticated workspace, load the stored object key server-side, and verify length/SHA-256 before returning bytes. The UI never receives bucket credentials. Target text, model output and event payloads are escaped as text; the static interface uses a same-origin content security policy.

## Run controls

Use **Stop run** on an active run or **Cancel queued job** before launch. The queue and run header show **Stopping…** while the worker acknowledges a durable request. Cancelled runs retain their evidence, and in-flight model usage may settle later. [Cancellation behavior](../exploration/cancellation.md) describes the API and restart recovery.

A failed, interrupted, blocked or cancelled exploration or reproduction offers **Run again** in its run header and as a restart icon in **Recent tests**; a tracked job that could not start offers **Try again**. Each submits a new job with the request that launched the original: the same URL, viewport, sign-in mode, automatic-check choice and project. Current saved settings apply, and the original run and its evidence are unchanged. A saved sign-in that has expired or been removed is left out, so the new run asks for sign-in. The control is hidden while the same test is queued or running, and on an interrupted run whose job continued in a later run. Fix verifications restart from their issue page. The workspace builds the request from the loaded job (latest 50), falling back to the run's recorded configuration for older runs.

For an opted-in source, **Stop automatic checks** remains available while planning, reservations or children are outstanding, even after the parent exploration finishes. It stops future automatic planning and records stop intent for existing child jobs and active child runs in one transaction. It leaves the original exploration and unrelated manual jobs alone. The source panel shows the acknowledged stop state; a narrow retry control is available if a child stop request is still unacknowledged. Already completed replay outcomes, actions and usage remain recorded. Stopping does not undo browser actions or cancel usage already sent to a model provider.

## Human finding review

The Findings tab filters pending, human-confirmed and dismissed candidates. Open an action to inspect its complete review history and record a reasoned decision. Confirmation requires verified reproduction evidence, an expectation basis and severity; it adds a separate human label and preserves the original AI assessment. Draft text survives refresh and concurrency conflicts. See [finding reviews](../exploration/finding-reviews.md).
